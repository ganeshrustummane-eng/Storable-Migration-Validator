# 0003. Where AI is actually used (YAML generation) vs. not (Run Validation) — investigation

**Status:** Investigation only — no code changed, nothing decided. For you to read and tell me what you want.
**Date:** 2026-09-23

## The question

You saw `[SQLQueryGenerator] AI generation active (model: gpt-4o)` printed
repeatedly right around when you clicked **Run Validation**, and want to know:
does Run Validation actually call an LLM? Your stated intent to the client is
"AI only builds the YAMLs; running validation is Python-only, no AI."

## What I found, traced by file:line — not guessed

### Run Validation contains zero AI code, confirmed by grep, not assumed

`webapp/app.py`'s "🚀 Run validation" button calls `runner.start_validation()`
(`Project/runner.py`), which launches `python main.py` **as a subprocess**,
cwd=`Project/`. That subprocess's entire import tree is:

```
Project/main.py
 ├─ Project/db/factory.py, db/*.py       (DB connectors)
 ├─ Project/utils/*.py                    (canonicalize_frames, quality_checks, row_compare)
 └─ Project/tiered_runner.py              (hybrid_v1 path)
```

I grepped all of `Project/` for `ai_sql_generator`, `SQLQueryGenerator`,
`AISQLQueryGenerator`, `openai`, `DIAL_API_KEY`, `gpt-4o`, `"AI generation"` —
**one hit**, and it's a code *comment* in `Project/tiered_runner.py` (line 8)
referencing `sql_query_generator.py` by name to explain where the SQL it
reuses was originally generated — it does not import or call that module.
Nothing in `Project/` can print the line you saw. **Run Validation is
Python-only, exactly as you told the client.**

### The line you saw comes from YAML generation, and it fires once per table

`[SQLQueryGenerator] AI generation active (model: ...)` is printed once, in
`SQLQueryGenerator.__init__` (`src/generated_queries/sql_query_generator.py:204`),
every time a `SQLQueryGenerator()` instance is created. Tracing who creates
one:

```
webapp UI (RPJ tab / batch generate / custom SQL tab / Excel batch loader)
  → src/validation_pipeline.py's run_with_plan()
    → src/generated_queries/yaml_config_writer.py
      → src/generated_queries/query_output_manager.py
        QueryOutputManager.__init__(): "Orchestrates SQL generation + YAML
        file output for a single table pair" (its own docstring, line 133)
        → self._sql_gen = SQLQueryGenerator()   ← prints the line, once per table
```

17 repeats of that line = 17 tables had their YAML (re)generated in that
batch — one `SQLQueryGenerator()` per table, not one per validation run. This
matches your paste: 2 "Extracted N columns" lines (schema extraction) then a
run of "AI generation active" lines — that's the signature of a YAML-generation
step (batch generate / RPJ / Excel batch), not Run Validation.

**Likely explanation for what you saw:** these are two different actions in
the same terminal scrollback. Streamlit's server process prints to one
console for the whole session; if you generated/regenerated YAMLs for 17
tables and then clicked Run Validation shortly after (without the console
being cleared), the AI-generation lines from the earlier step are still
sitting there above whatever Run Validation itself printed, making it look
like Run Validation caused them.

### A real discrepancy worth flagging, separate from your question

`SQLQueryGenerator.__init__` (`sql_query_generator.py:181-185`) **hard-fails**
if you try to construct it with `use_ai=False`:

```python
if not use_ai:
    raise AISQLGenerationError(
        "SQLQueryGenerator(use_ai=False) is no longer supported. "
        "Validation SQL is AI-generated only."
    )
```

That means the *SQL text itself* (the actual `sourcequery`/`targetquery`
strings baked into the YAML) is generated by an LLM call for every table,
unconditionally — not just for resolving ambiguous column names. This is a
narrower, still-real AI dependency than "AI only for ambiguous columns"
(CLAUDE.md's description of `validation_pipeline.run_with_plan()`) suggests —
column *matching* is exact/fuzzy-first with AI only on ambiguous columns, but
the SQL *text generation* step underneath it currently requires AI every
time, for every table, with no static/deterministic fallback. This is not the
same thing as the old fully-removed `ai_transformation/orchestrator.py`
100%-AI pattern CLAUDE.md warns not to resurrect — this is a different, still
very much alive file — but it's worth you deciding whether "AI only for
ambiguous columns" is still an accurate claim to make to the client about the
*generation* step, separate from the Run Validation question you actually
asked about.

## Bottom line

- **Run Validation: confirmed Python-only.** No AI import, no AI call,
  anywhere in the subprocess it launches. Safe to keep telling the client
  that.
- **YAML generation: AI is mandatory**, not optional, for the SQL-text-building
  step (`SQLQueryGenerator`), on top of being used for ambiguous column
  matching. If "AI only for ambiguous columns" is part of what you tell the
  client, that claim is narrower than what the code currently does.
- Nothing changed in this investigation — tell me which of these (if either)
  you want addressed, and how (e.g. reduce the printed noise, add a
  static/no-AI fallback path, or just correct the client-facing description).
