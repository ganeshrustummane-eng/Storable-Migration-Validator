Migration Validator — Column-Mapping Pipeline

Scope: schema extraction → column matching → cloud-assisted YAML/SQL config generation through a Python script. This document covers generation only.
Data-exposure summary: The only thing ever sent to the Claude API is column metadata — column name, data type, and ordinal position — for a small number of columns the deterministic matcher couldn't confidently resolve on its own. No table rows, no cell values, no credentials, and no PII ever leave the network boundary. Most columns never reach the AI step at all; they're resolved locally by exact/fuzzy name matching.
Data source (schema-only reads) Local processing — no network egress Resolved without AI Claude API — metadata only crosses here Output artifact

What crosses the network boundary to Claude

  • Sent to the cloud generation service: schema and mapping metadata (column names, data types, ordinal positions, candidate columns, and active source-to-target mappings), excluded-column instructions, applicable data/normalization rules, Fivetran-active filtering, source/target filters, and optional JOIN instructions. The AISQLQueryGenerator in src/generated_queries/ai_sql_generator.py uses this context to generate dialect-specific SQL and the associated YAML configuration.
  • Never sent to Claude: table rows, cell values, database credentials, connection strings, or any PII. The AI step only runs for columns the deterministic matcher (exact name match → fuzzy name match → confidence scoring) couldn't resolve on its own — most tables need zero or very few AI calls.
  • Returned by Claude: which candidate column matches, a transformation-rule identifier (e.g. "currency_conversion"), a confidence score, and a short text reason — all metadata, no source data reflected back.

What is this tool?

  • Not open source, not an EPAM product, not a third-party SaaS tool. It's custom software written in-house for Storable's own migration-validation problem, living in this Storable git repository. It is not distributed, resold, or run by any outside company.
  • It's built on top of standard open-source libraries (RapidFuzz for fuzzy matching, Streamlit for the UI, pandas/pydantic for data handling, psycopg2/pyodbc/boto3/snowflake-connector-python as database drivers) — these are dependencies, not the product itself, and none of them transmit data anywhere.
  • The third-party cloud service used for generation is an AI API — today EPAM's DIAL proxy (used during initial build/test only), moving to Anthropic's Claude API directly once a Storable-issued Claude key is available. The Python script sends the limited metadata needed for mapping and generation, then writes the resulting YAML/SQL configuration locally.

Deployment

  • Local script, run by the engineer doing the review — today's actual usage. The Streamlit UI is started with streamlit run webapp/app.py on the engineer's own machine or a shared internal VM; there's also a plain CLI entry point (python -m src.validate_cli).
  • A Docker image also exists in the repo (root Dockerfile) for a separate, optional containerized deployment path (e.g. Cloud Run) used by a different feature in this repo. It is not required for the Claude API key request.
  • Either way, the process runs inside Storable's own network/machine and holds its own DB and Claude credentials via a local .env file (git-ignored) — no separate hosting party is involved.

Cost limiting for AI usage

  • Call volume is minimized by design, not by a bolt-on limiter: every column is first run through deterministic exact-name and fuzzy-name matching (RapidFuzz) locally, at no cloud API cost. Only the columns that matching still can't confidently resolve — typically a small minority — ever reach the cloud generation service.
  • Each AI call is small and bounded: one call per ambiguous column (no batch/looping calls), the prompt includes only that column's metadata plus its top 5 candidate columns (not the whole schema), and the response is capped at max_tokens=1024.
  • No runaway retries: if a call errors or returns something unusable, the code falls back once to the best fuzzy-match candidate — it does not retry the API in a loop.
  • Usage is logged for visibility: every real AI call's prompt/completion token counts are appended to token_usage_analysis/logs/token_usage.jsonl, so spend per validation run can be reviewed after the fact.
  • Gap, stated plainly: there is currently no hard pre-set spend/call ceiling (e.g. a max-calls-per-run or daily-budget cutoff) enforced in code — only the architectural minimization above and after-the-fact logging. If Storable's approval requires a hard cap as a condition, that's a small, addable control (e.g. an env-var call ceiling checked before each AI call) that does not exist yet today.
